The canonical shared knowledge vault for the AMLHive fleet. Every local MemPalace
store (Windows gumby chambers, main chambers, Hermes mempalace-inputs, Hermes
ops decisions) feeds INTO this private GitHub repo; all systems and agents read
from and push to it going forward. It is the git-backed, machine-shareable,
Claude/Gemini-readable form of Mempalace 2.0.

## Data flow (single-writer push)

```
Windows gumby chambers/  ─┐
Windows main chambers/   ─┼──►  ~/.hermes/scripts/alexandria_sync.py  ──►  git push origin main
Hermes mempalace-inputs/ ─┤            (WSL cron fc726783497f, 4x daily)
Hermes ops/ decisions/   ─┘
Hermes cron outputs/     ─┘      (every report job → vault/reports/<job-name>/)
```

- **`git fetch` and check the behind-count BEFORE you author anything — this clone is routinely many commits stale.** The scheduled sync pushes 4×/day and sibling sessions commit between runs, so a session that merely opens the clone can be ~100 commits behind `origin/main` (observed: 95 behind). Authoring against a stale tree makes you re-file a note a sibling already filed, cross-link against a superseded map, or produce a diff that appears to delete their work. First move on any vault write: `git fetch --quiet origin`, then `git rev-list --left-right --count origin/main...HEAD`; if you are behind and 0 ahead, `git pull --ff-only origin main`. Only then read the tree you are about to edit. (Distinct from the writer-race check below — that guards against a *live* writer mid-commit; this guards against a stale *starting point*.)
- **Writer discipline:** the two WSL crons (alexandria_sync.py + alexandria_report_sync.py) are the scheduled pushers — but sibling Hermes/agent sessions ALSO commit to this same clone (e.g. large `library/` harvests). Before any manual commit or drain run: `ps aux | grep -E "alexandria_sync|alexandria_report_sync"` **and** `ps aux | grep -E "git (commit|push|add)"`, and check `.git/index.lock`. **Grep the sync SCRIPT names, not just git** — a running sync spends almost all its wall-time walking and copying files and only briefly shells out to git, so a git-only check taken at the wrong instant reports nothing while the writer is very much live. If a sync IS running, do **not** commit concurrently: its own `git add -A` will sweep up both its changes and yours in a single commit — racing it only risks a half-staged tree. Wait out the other writer; never delete its lock, never force around it. Local stores on other machines keep existing; alexandria is the aggregation + history + sharing layer, not a replacement for local working stores.
- **Scope every git add to your own tree — never `git add -A` in this clone.** Sibling sessions keep large uncommitted work in the same working dir (`library/`, `vault/refined/`, chambers). `alexandria_report_sync.py` stages only `vault/reports` (`git add -- vault/reports`); keep it that way. A single `git add -A` in a shared clone commits another agent's half-finished work under your message.
- **This clone is SPARSE — out-of-cone tracked files appear as phantom deletions, and an ordinary `git add` silently refuses them.** `sparse-checkout` is `/*` with `!/vault/reports/*`, so the ~1,400 report files that DO exist in `origin/main` are absent from the worktree: `git status` reports them ` D`, and `git add vault/reports` answers `matched paths that exist outside of your sparse-checkout definition, so will not be updated in the index` while staging nothing. **Never stage those deletions — committing them deletes real report history from the repo.** To fold in a reports-lane batch: (1) enumerate with `git status --porcelain -z` and split `??` (genuinely new) from ` D`/` M` (phantom, i.e. outside the cone); (2) confirm each phantom still exists upstream with `git cat-file -e origin/main:<path>` before touching it; (3) `git update-index --skip-worktree -- <phantom paths>` so they stop reporting; (4) `git add --sparse -- <new paths>` — the `--sparse` flag is the only thing that lets git index paths outside the cone; (5) scoped commit + push. Verify after: `git rev-parse HEAD` == `origin/main`, **and** `git cat-file -e origin/main:<a phantom path>` still succeeds (proof you did not delete it).
  **Two more faces of the same cone, both silent — check them whenever a script writes into this clone.** (a) A WRITER whose destination is outside the cone produces files git will never stage: the drain copied 635 reports into `vault/reports` that `git add -A` skipped, so they sat unversioned on a single disk while every run reported success. Prove a lane is really tracked with `git ls-files <dir> | wc -l` against the on-disk count, not with `git status` alone. (b) `git rm -r --cached --quiet <out-of-cone path>` ALSO refuses (prints `hint: ... Disable or modify the sparsity rules`) and under `--quiet` stages nothing while looking like success — removal requires `git rm -r --cached --sparse`, and re-adding the keeper file beside it requires `git add --sparse -f`.
- **Do not `git ls-tree -r origin/main` on these repos to inspect a tree — it dumps every path.** On `alexandria-ops` (1,400+ report files) that is >120KB in one tool result and blows the output window. List one subtree (`git ls-tree -r --name-only origin/main -- insights/`) or just count (`... | wc -l`).
- **Readers:** any machine/agent (Claude, Gemini, ChatGPT, another OS) clones the
  repo read-only for knowledge.
- **Precedence:** gumby chambers are canonical; main-store chambers only merge in
  when a file is absent or strictly larger (never overwrite richer gumby content
  with a stub).

## Cron reports drain → `alexandria-ops/reports/` (NOT this vault, since 2026-09-21)

Raw cron exhaust belongs to **`haris-admin/alexandria-ops`**. It used to drain into `vault/reports/`; that lane was evicted 2026-09-21 (see the eviction paragraph below). What remains here is only the pointer `README.md` and curated `_rollups/`. The old drain's semantics — now applied by `alexandria_ops_sync.py` in the ops repo — were: every cron job outcome lands in one folder per job, the 6-hourly fleet monitors
(5/11/17/23: AmLHive AWS, TapEase, Pluto) plus all daily/weekly report jobs,
test suites, probes. Job folders use readable names mapped from
`~/.hermes/cron/jobs.json` (not raw job ids); same-named jobs across products
merge into one folder (safe — output filenames embed the timestamp). Bounded
newest 60 files per job folder; root-level chunked `.txt` overflow files go to
`vault/reports/_chunked-outputs/` (newest 30). Index lists recent reports.

**Retention is count-based ONLY (newest 60 per folder) — never add age-based
pruning.** The vault deliberately keeps deep history (daily jobs span months); a
30-day age-prune deletes legitimate old reports that the canonical design keeps.
The full vault sync and the report-archive cron must share the same bound so
folders don't thrash between them.

**The one refinement: retain-by-value tiers (verified by vault/reports audit
2026-09-08), applied per JOB class, not globally.** Keep-newest-60 is right for
signal jobs (research, briefings, fleet monitors, syncs — daily content that
actually changes); it is wasteful for jobs whose output is a status line. The
noise classes to cap aggressively: empty-output/silent jobs (3 hourly probes
+
5-min watchers emit a ~170B "Status: silent" file every run — cap at ≤3 or keep
only non-silent runs), status-redundant jobs (same failure/txn-count line every
day — keep 7-14 days or just last-success + last-failure), and mostly-empty
signal jobs (e.g. Competitor Intel where 75% of runs say "no signals detected"
— keep signal-bearing runs + a rolling 14-day window). Never age-prune the
signal classes. An audit report (`vault/refined/audit-reports-20260908.md`)
gives per-folder uniq-ratios to classify jobs empirically (ratio ≈1.0 = novel
daily content = signal; ratio ≤0.1 = status/empty = noise).

**Folder names must be Windows-safe ASCII — colons, emoji, slashes and trailing
spaces corrupt the vault for Windows git clients.** The repo is reviewed on the
Windows side; NTFS/DrvFS strips invalid chars (job `"6:00 AM"` → folder
`"600 AM"`) so WSL-clean paths appear as phantom deletions/duplicates to Windows
git. Sanitize every job-name-derived folder exactly once, deterministically:
keep ASCII letters/digits and safe punctuation, drop emoji + variation selectors
(☿ 🪐 🪟 ★), strip `: * ? " < > |`, and replace `/` with ` - ` (a `/` inside a
folder name makes git build a NESTED tree — `"ASIC / Ref-DB"` became
`Pluto ASIC/ Ref-DB Sync/` on disk). A sibling sanitize pass (eb27c8a) already
renamed 39 folders — any new drainer must reproduce that exact naming or it
recreates duplicate emoji dirs on top of the clean ones.

**Prune and "newest" selection by FILENAME, never mtime.** Report filenames are
`YYYY-MM-DD_HH-MM-SS.md`, so lexicographic sort IS chronological. Git checkouts
reset file mtimes, so an mtime-sorted prune keeps freshly-restored OLD files and
drops genuinely-new ones (observed: July reports kept, Sep reports deleted).

**When several cron jobs share one destination folder** (the 4 monitor runs all
map to `AmLHive AWS Fleet Monitor`), group source dirs by folder, copy, then
prune ONCE per folder to the bound — pruning per source job dir makes later jobs'
copies evict earlier jobs' files unevenly.

**A drain interrupted mid-commit leaves hundreds of staged deletions.** If a git
lock aborts a drain run after its prune step, restore the tree
(`git restore --staged --worktree vault/reports`) and re-run the corrected
script — do NOT commit the half-applied prune state.

**Before evicting ANY batch of tracked files, prove each one exists somewhere else — the safety gate is not optional.** A batch that looks like pure duplication routinely is not: the report drain had written 635 files into `vault/reports` that `git add -A` never staged (out of the sparse cone), so those files existed ONLY in that one working tree, and a naive delete would have destroyed them. Report the residue count to the owner instead of asserting "it's all duplicated".

**The 2026-09-11 → 2026-09-21 outage (the whole point of `alexandria_ops_sync.py`):** the Sep-9 migration copied a batch into `alexandria-ops` (1,419 files) but the ONGOING writer was never repointed, so ops went dead and every new run kept draining into the vault instead. A repo that exists and has history can still be a dead feed.

Any new drainer MUST do the same, or every job gets a second twin folder and the history splits in two.

## Sync script conventions

- Copy-on-change (size compare) — idempotent; no changes → no commit.
- Uses `git -c user.name=Mercury Sync -c user.email=mercury-sync@amlhive.local`.
- Keeps newest `MAX_INPUTS=40` filings in `vault/inputs`, prunes older.
- Refreshes `vault/index.md` every run.
- Auth comes from `~/.git-credentials` (OPERATOR PAT) — do NOT store a token in
  the remote URL; strip it after a token-bearing clone
  (`git remote set-url origin https://github.com/haris-admin/alexandria.git`).
- **Commit-message convention (match existing history, per repo `AGENTS.md`):** `sync(alexandria): …` for sync/archive drains, `chore(alexandria): refinery — <task> (<n> files)` for refinery-queue batches, and `feat(alexandria): …` / `fix(alexandria): …` / `docs(alexandria): …` / `chore(alexandria): …` otherwise. A hand-rolled `vault(refined): …` prefix is OFF-convention — use `docs(alexandria): <what landed>` for new knowledge notes and `fix(alexandria): <what was wrong>` for frontmatter/correctness repairs.

## Pitfalls

- **Bound the MERGED candidate set before copying, or the drain churns forever.** Several source dirs under `~/.hermes/cron/output/` can resolve to ONE destination folder (a raw job-id dir plus a readable-slug dir). Merging them exceeds the retention bound, so if you trim only AFTER copying, the prune deletes the overflow and the very next run copies it straight back: every run reported `281 copied, 279 pruned` and committed ~560 file-changes — 4×/day of pure noise, forever. Fix: `src_files = sorted(src_files, key=os.path.basename)[-MAX:]` on the merged list BEFORE the copy loop. **Test idempotence explicitly: run the drain twice and require the second run to report `0 copied, 0 pruned`.** A drain that is not a fixed point is broken even when its output looks correct.
- **A refused `git commit` must fail the run, never report success.** Symptom seen 2026-09-21: a manual drain overlapped the cron fire, `git commit` died on `.git/index.lock` (`Another git process seems to be running in this repository…`), the script carried on and pushed — and the scheduler recorded `last_status=ok` while that drain's work sat uncommitted. Retry the commit with a short backoff (an index.lock clears in seconds), then assert `git status --porcelain -- reports` is EMPTY before pushing; if it is not, print an ERROR and exit non-zero so the job shows as failed. Same class as the stale-memory bug: a green report over work that did not happen.

- **`git push` can fail from inside a Hermes tool session while working perfectly from cron — use the Windows git binary as the fallback.** Symptom: `fatal: the remote end hung up unexpectedly`, `send-pack: unexpected disconnect while reading sideband packet`, and `error: waitpid for git-remote-https failed: No child processes` (ECHILD) — while `curl https://github.com` returns 200 and the same push from a bash script or the scheduled cron succeeds. It is a signal/PATH quirk of the tool process tree, not auth and not a network fault, so do NOT start rotating tokens or rewriting `~/.git-credentials`. The local commit already holds the work; push it with the Windows binary instead: `"/mnt/c/Program Files/Git/cmd/git.exe" -C 'C:\\Code\\github\\haris-admin\\<repo>' push origin main` (verified working 2026-09-21). `alexandria_ops_sync.py` bakes this in as an automatic fallback.

- **A knowledge file that refuses to stage is being swallowed by a secrets guard, not rejected by git.** The `.gitignore` this repo is set up with uses broad globs (`token*`, `secret*`, `credential*`, `*.env`). Those match legitimate knowledge filenames as well as real secrets — `token*` silently blocks any note about card/network **tokenisation**, tokenised settlement, tokenomics or token lifecycle (hyphen or not, `*token*` matches mid-word). The file sits on disk, `git add` reports only "The following paths are ignored", and a commit with nothing staged "succeeds" — so the knowledge never lands and nothing looks broken. When a note will not stage: run `git check-ignore -v <path>` first, then confirm it is actually tracked afterwards with `git ls-files <path>`. Fix by exempting the authored tree, not by weakening the guard globally — keep real-secret coverage on the external `library/` mirror and exclude only our own vault: `!vault/**/*token*`. Any narrowing must stay scoped the same way; never widen a secret guard across `library/` to make one file commit. When you introduce a secrets guard, prefer anchoring the pattern (`*token*.json`, `*.env`) over a bare mid-word glob.
- **Validate frontmatter against `vault/_refinery/frontmatter.schema.json` BEFORE committing — `tier` and `type` are different enums and are easy to swap.** `tier` ∈ {canonical, refined, log, raw, ephemeral}; `type` ∈ {signal, intel, research, digest, reference, adr, moc, report}. Writing `type: log` (a *tier* value) violates the contract and NOTHING rejects the commit — the file just silently breaks the schema, so a later refinery pass or index build trips on it. Required keys: id, title, tier, type, domain, source, created, updated; optional enum keys: status, confidence, owner (put `owner: mercury` on notes this agent authors). Verify by parsing the frontmatter block and asserting every `required` key is present and every enum-keyed value is in its enum (a 15-line check — cheaper than a refinery regression).
- **A second read-only clone (`/home/habib/code/alexandria`) is EXPECTED to lag `origin/main` — never push from it.** The WSL sync script's checkout (the one whose remote carries the PAT, `/mnt/c/Code/github/haris-admin/alexandria`) is the only writer that pushes; per `AGENTS.md` every other clone is read-only knowledge, so a stale or diverged reading there is not a fault to fix. Never force-push or rewrite history to reconcile a clone. When authoring manually and the sync/other agents have pushed meanwhile: `git fetch` → confirm the incoming commit does not touch your paths → `git -c user.name=… pull --rebase origin main` → push.
- **Never put agent-instruction files in the vault** — writing
  `.claude/CLAUDE.md` inside the alexandria clone is BLOCKED by the Hermes
  protected-instruction-file filter (write approval times out). Write the same
  orientation content as `vault/AGENT-GUIDE.md` (a normal doc) instead.
- **Repo defaults to PUBLIC on API creation.** The GitHub API creates a new org
  repo public unless `private: True` is passed explicitly (user corrected
  "Is private" — the empty repo had been created public). Always pass
  `{'private': True}` on create and re-verify with `repo.get('private')`.
- **On this estate, create repos with `POST /user/repos` — never `/orgs/<name>/repos`.** `haris-admin` is a USER account, not an organisation, so the org endpoint answers `404 Not Found`; that reads exactly like a missing-scope/permission failure but is an endpoint-shape error, and chasing the "permission" problem wastes the session. The OPERATOR PAT resolves to the `haris-admin` user, so `POST https://api.github.com/user/repos` with `{"name": …, "private": true, "auto_init": false}` creates it under the right owner. Verify with `GET /repos/haris-admin/<name>`, and if you POSTed a throwaway name to probe the endpoint, `DELETE /repos/haris-admin/<name>` it in the same session — do not leave probe repos behind.
- **Repo lists come from `/user/repos?affiliation=owner,collaborator,organization_member`, not an org call** — repos hang off the user PLUS collaborator repos owned by other accounts. Repo OWNER, org, and account type are three different things here; establish which one you are addressing before concluding a repo is missing.
- **`gh` CLI is not authenticated** on this host — use the API with the OPERATOR
  PAT header (`Authorization: Bearer <pat>`, `Accept: application/vnd.github+json`)
  or git with `~/.git-credentials`, not `gh repo create`.
- **Check visibility + contents BEFORE assuming empty:** a "new" repo may already
  exist (created from the GitHub web UI); read `pushed_at`/`contents` before
  initializing a conflicting structure.
- **Never commit the Chroma/bin/sqlite stores themselves** — alexandria is
  markdown-only. The old `haris-admin/openclaw` repo committed raw Chroma `.bin`
  blobs (3.5 months stale as of the 2026-09 initial build) — that pattern is what
  alexandria replaces.
- **The live Windows `knowledge_graph.sqlite3` is WAL-locked by its writer** —
  do not attempt SQLite reads on it; use the file-based chamber stores
  (`workspace-gumby/mempalace/chambers/*.md`) which are always readable.
- **`git add -A` sweeps in unrelated untracked content** — never use it in this
  clone (see writer-discipline rule above for the scoped-add fix). If the
  external `library/` mirror was already committed once (2050 files), remove it
  once with `git rm -r --cached library` + add `library/` to `.gitignore`;
  then keep every future add scoped.
- **Windows-mounted repo git ops are slow** — generous timeouts (120s+) on git
  commands here; prefer the script's batched commit+push over ad-hoc per-file git.
- **When origin has restructured the vault, reconcile by resetting to origin then re-applying ONLY your unique content — never hand-resolve a dozen rebase conflicts.** Sibling sessions restructure the vault (explicit moves, e.g. `vault/decisions/` → `vault/canonical/decisions/`); a stale clone's mechanical sync-mirror commits were written against the OLD layout and collide with those commits. Fix: `git reset --hard origin/main`, then restore only content that is yours and NOT on origin with `git checkout <your-sha> -- <path>/` (a fresher `library/` mirror; a CHANGELOG entry re-applied by hand), then commit. Mechanical mirror content regenerates on the next sync run; the canonical restructure does not. Confirm the delta with `git diff --stat origin/main..HEAD -- <path>` before and after so you can see exactly what you are keeping versus dropping. When you hold ONE commit worth keeping and the local base is merely stale, prefer `git rebase --onto origin/main <old-base-sha>` over a reset: it replays only your commit onto the true remote and drops the superseded local sync commits, with no force-push and no hand-resolution. Fetch with the WINDOWS git binary first if the WSL fetch is failing — a stale `origin/main` ref makes a perfectly fast-forwardable commit look rejected, and mis-diagnosing that wastes the session.
- **`push rc: 1` / `non-fast-forward` is a SECOND-WRITER collision, not an auth failure.** Sibling sessions and hand-edits push `origin/main` too (observed 11 Sep 2026: a manual `Update startup-ventures.md` commit landed on origin while the local clone held 4 uncommitted-by-local sync commits). The error text is `Updates were rejected because the tip of your current branch is behind`. `alexandria_sync.py` now self-heals: on a rejected push it runs `git pull --rebase --autostash origin main` and retries up to twice, aborting the rebase cleanly on conflict. **The `--autostash` is load-bearing (fixed 2026-09-17): without it the retry always died with `error: cannot pull with rebase: You have unstaged changes`** — the harvest writes files right up to the commit, so unstaged churn is present at push time, and the abort/return-1 path fired even though NOTHING had conflicted. Symptom to recognise: `push rc: 1` followed by `rebase failed: ... cannot pull with rebase: You have unstaged changes` is a STUCK WRITER, not a content conflict — the clone silently accumulates unpushed commits (found 5 ahead / 2 behind after a day of failing runs) while every cron output looks like an ordinary non-fast-forward. Diagnose with `git rev-list --left-right --count origin/main...HEAD`: a rising left number means the same push has been failing for days. A genuine conflict still aborts and prints `⚠️ MERGE_NOT_APPLIED` (BLOCKED) — do not resolve it by hand. Manual repair of a stalled clone: `git stash push -- <file>` for any dirty file, `git pull --rebase --autostash origin main`, `git push origin main`, then re-apply the stashed content ON TOP of the remote version (both are usually additive changelog appends — keep both blocks, do not pick a side) and commit.
- **Never run this repo's `pull --rebase` under a short tool/command timeout.** Replaying mechanical mirror commits of 3,000-4,700 files each on DrvFs takes minutes — longer than a 180s cap. A killed rebase leaves `.git/rebase-merge/` behind with `autostash` recorded and a partially-checked-out worktree (thousands of phantom ` M` files), which reads alarmingly like data loss but is not: `orig-head` and `HEAD` are both still your pre-rebase tip. **Recovery: `git rebase --abort`** — it resets to `orig-head` and prints `Applied autostash`, restoring the exact prior state (verified 2026-09-17: HEAD unchanged at the pre-rebase SHA, dirty count back to its prior value, 0 conflict markers). Confirm with `git rev-parse HEAD` == `cat .git/rebase-merge/orig-head` before aborting if you want certainty. Then let the SCHEDULED sync run (00:24 / 06:24 / 12:24 / 18:24) do the drain — it has no such timeout. Do not hand-drain a huge mirror backlog in a session with a command timeout.
- **`git stash list` is empty even while an autostash is pending** — autostash records its commit SHA in `.git/rebase-merge/autostash`, NOT in `refs/stash`. Absence from `git stash list` is therefore not evidence that the churn was lost.
- **`push rc: 0` is NOT proof the push landed — verify against the REMOTE.** Observed 2026-09-21 18:23: the vault sync committed `a72ec3dd`, printed `push rc: 0`, and the commit stayed local while `origin/main` remained on the previous SHA (this host's WSL git intermittently loses the transport without failing the command). Check with `git ls-remote origin main` (authoritative — no local ref involved; a local `origin/main` can be stale because WSL `fetch` is also unreliable here) and compare to `git rev-parse HEAD`. `alexandria_sync.py` now self-verifies via `_push_landed()` and falls back to the Windows git binary (`/mnt/c/Program Files/Git/cmd/git.exe -C 'C:\Code\github\haris-admin\alexandria' push origin main`), exiting 1 if the commit still is not published — so an unpublished sync shows as FAILED instead of green. When a cron output looks green but a reader sees stale content, suspect this before suspecting the reader. **Never test a git command through a pipe** — `if git push origin main | tail -3; then` tests `tail`'s exit status, not git's, so a REJECTED push printed "pushed" and skipped the fallback that was supposed to save it; the only reason it was caught is the explicit HEAD-equals-origin read-back. Branch on git's own status or on the read-back, never on the pipeline.
- **A Python write error can leave a knowledge file TRUNCATED to 0 bytes — size-guard every vault write BEFORE you stage it.** `Path.write_text()` opens in mode `w` (which truncates immediately) and only then encodes, so an exception during encoding leaves an EMPTY file on disk; if the commit was already prepared, you push a 0-byte document and the real content survives only in history. Observed 2026-09-20 on this repo: `lms-market-australia-brightspace-20260920.md` went from 16,348 bytes to 0 in a pushed commit because the generating script contained emoji written as escaped surrogate pairs (`\ud83d\udd36`) — Python builds lone surrogates from those and cannot encode them to UTF-8. Three rules: (1) in any script you generate, write emoji/non-ASCII as LITERAL characters, never as `\u` surrogate-pair escapes; (2) assert the on-disk size against the previous version (`os.path.getsize(...) >= <prior>`) before `git add`; (3) after staging, assert the STAGED blob size with `git cat-file -s :<path>` — an empty staged blob is the last abort point. Recovery is cheap if you catch it: `git show <good-sha>:<path> > <path>`, re-apply the intended edit, commit as a `fix(alexandria):` with the truncation stated in the message. A size check is the only guard that catches this class — a clean `git status` reports a truncated file as an ordinary modification.
- **Script-path references in skills may point at the WINDOWS scripts dir.** `~/.hermes/scripts/` (WSL) and `/mnt/c/Users/habib/.hermes/scripts/` (Windows) hold DIFFERENT files — e.g. `pluto_monthly_strategy_job.py` and `send_strategy_professional_email.py` exist only on the Windows side. A "missing script" verdict from checking only the WSL dir is a false positive ~100% of the time; check both roots before flagging.
- **`Repository not found` on a push/fetch is usually an AUTH problem, not a deleted repo.** When a repo that pushed fine minutes earlier starts 404ing "repository not found", check `~/.git-credentials` ownership before suspecting the remote: a sibling session/script can overwrite the file with a DIFFERENT account's token (observed: haris-a2squre/Tapease PAT clobbered the haris-admin operator entry mid-session — private-repo anonymous fetch then reads as "not found"). Check `.git-credentials` mtime — a rewrite mid-session is the tell. **Two consequences that decide how you sequence the work.** (1) **Push immediately after the scoped commit — never batch the push to the end of the session.** A sibling can clobber the store at any moment, so a clone that pushed an hour ago can start 404ing with nothing on your side having changed. Leave the work as a **local scoped commit** (the commit is the safe landing point: nothing is lost, it is merely unpushed), then report the blocker with the exact error text and the commit SHA for the owner to clear. A stalled push is a reportable blocker, not a session-ending problem.

## Creating a NEW chamber (venture/project/topic chamber)

Owner habit: a new venture/project gets its own chamber (or one ventures chamber listing them all — Simplify/Simplifii, Undispute, Step Up, Tigris, AMLHive, TAPEase — filed under the topic parent, e.g. startup-ecosystem). To create one that survives the sync AND lands on GitHub:

2. 5. Add a dated `### YYYY-MM-DD` pointer in the parent chamber's Signal Log so the new chamber is discoverable from the topic it sits under.

## Dated artifacts: confirm the date, never inherit it

- **Run `date '+%Y-%m-%d %H:%M:%S %Z (%A)'` immediately before you name a dated file or
  write `created:`/`updated:`.** A long-running session's context block goes stale — its
  "today" can be a day or more behind wall-clock while the workspace keeps moving — and a
  document filed under the wrong date is indistinguishable from a real historical record
  to every later reader. Corroborate cheaply: the newest cron output timestamps and the
  scheduler's own next-fire times will disagree with a stale date.
- **When the artifact summarises an external source whose own edition date cannot be
  verified, name it by the FILING date and put the content window inside the document**
  (e.g. "newest cited item dated X — treat the content as as-of ≤X"). Do not infer the
  source's edition date into the filename.
- **Do not burn the session hunting an unverifiable source edition.** Greps across cron
  output, `mempalace-inputs` and `research_outputs` for a distinctive string can run for
  minutes and still return nothing decisive. The git commit time of the filed document is
  the authoritative record of *when* it entered the vault; state that, and move on.
- **If you filed under the wrong date, correct it as ONE scoped commit** — `git mv` to the
  corrected name plus the frontmatter patch together (git reports it as a rename, so
  history is preserved), verified afterwards with HEAD == `origin/main`. Never leave the
  stale dated filename in place with a note beside it.

## Where canonical artifacts live (don't invent new top-level dirs)

- **Meeting notes / call transcripts for a venture belong in `vault/refined/<venture>/` behind a folder `README.md` index.** File the digest — decisions, action items, dated milestones, who-owns-what — as the main note, and cross-link the companion analysis and founding brief by relative path. Two rules that make these safe to rely on later: (1) the source transcript is **computer-generated** — stamp the note as such and treat names, numbers and terms as unverified until a primary source confirms them (a third party's contract value is an *estimate* unless the contract was disclosed); (2) make the folder `README.md` the entry point (a `Contents` table plus the key rules to carry forward), so a later agent lands on the index rather than on one dated note inside a folder of many. When the owner forwards a companion doc that cannot be read (a private page not shared with the integration), record the reference *and* plainly flag that it was not ingested — do not silently omit it. When the source is a **Notion memo page** (meeting notes / call transcript the owner pastes into Notion), follow `references/notion-memo-filing.md` — it carries the markdown normalisation, the structural section-extraction rule (a memo commonly holds the same content twice; assert the extracted length before writing), the dictated-number reconciliation rule, and the tail-paginated read-back that proves an append landed.
- **An ideas-backlog entry** goes in `vault/refined/haris-admin/keep/ideas/<slug>/` — a `README.md` (status, score, trigger, related) plus `docs/` for the depth. Register the slug in BOTH indexes or it is effectively invisible: the MOC `vault/00-maps/startup-ventures.md` and the tracker `vault/chambers/startup-ventures.md`.
- **Dated regulatory obligations** live in `vault/canonical/reference/au-regulatory-calendar.md` — the single source for AU regulatory dates. It is `canonical: true`, so **do not rewrite a row in place to change its confidence**: add a new row for a new date, and for any changed or superseded entry append to the `## Corrections log` with `supersedes:` + `contradiction: true`. When a primary source finally lands for a date recorded as `medium — need official source before use`, upgrade that row's confidence and log the upgrade (confidence changed, the date did not).

## When to run

- After any chamber update in a local store (manual sync, or wait for the cron)
- When asked "is the knowledge in git / readable by another machine / Claude"
- When setting up a new machine that should share fleet knowledge
